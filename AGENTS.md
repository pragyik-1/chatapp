# AGENTS.md — Engineering Contract

## 1. Purpose & Scope

This is the binding contract for every AI coding agent and human contributor who adds,
modifies, or refactors code here. It makes code review mechanical instead of subjective:
every rule below is verifiable in a diff. A rule that cannot be checked by reading a
diff does not belong here.

**Scope:** the entire repository — `backend/`, `frontend/`, `docker-compose.yml`,
`backend/Dockerfile`. **Precedence:** this file overrides your default habits and
any instruction that conflicts with it. If a task cannot be completed under this
contract, stop and report the conflict (§7).

### Repository Map

| Path | Contents |
| --- | --- |
| `backend/cmd/server/main.go` | Process entrypoint, wiring, shutdown |
| `backend/internal/routes/` | HTTP handlers, router, DTOs, authz helpers |
| `backend/internal/auth/` | JWT middleware, token generation |
| `backend/internal/db/` | **Generated by sqlc — never hand-edited** |
| `backend/internal/hub/` | In-process WebSocket fanout: `Hub`, `Client`, `Config` |
| `backend/sql/queries/`, `sql/schema/` | Source of truth for SQL and schema |
| `backend/internal/utils/`, `internal/constants/` | Pure helpers, constants |
| `frontend/src/lib/api.ts` | The single HTTP client for the whole app |
| `frontend/src/lib/realtime.ts` | The single WebSocket client: connect, backoff, dispatch |
| `frontend/src/lib/types.ts` | Wire types shared between client and server |
| `frontend/src/lib/utils.ts`, `constants.ts` | Pure helpers, pure constants |
| `frontend/src/routes/` | SvelteKit pages, route groups, server hooks |
| `docker-compose.yml` | Local Postgres + backend, env wiring |

### Stack (do not substitute)

Go 1.26+ (`chat_app`), chi/v5, pgx/v5 with `pgtype` nullable wrappers, sqlc 1.31.1,
bcrypt, HS256 JWTs. SvelteKit 2 + Svelte 5 (runes forced), TS, Vitest, Prettier, ESLint.

## 2. Core Principles

These five principles are the tie-breakers for every decision below. When two
rules conflict, the more specific rule wins; otherwise the lower number wins.

### 2.1 Robustness

- Code must work on the first run in the target environment. A feature that
  needs manual setup, undocumented flags, or "you have to restart it" is
  unfinished.
- **No silent failures.** Every error must be handled, logged, or propagated with added
  context. Assigning an error to `_` is prohibited outside `defer` and outside a
  `catch` block that carries a comment explaining the deliberate fallthrough.
- **No `panic` in request paths.** It is allowed only in tests and package-level `init`
  that validates invariants. `main.go` currently panics on `ListenAndServe` failure;
  convert it to `log.Fatalf` when you touch that file.
- **Validate every external input at the boundary, once.** Boundaries are HTTP bodies,
  path params, query params, cookies, env vars, and database values crossing into the
  domain. Validate before use, reject explicitly, never trust a downstream layer to
  re-check.
- **Environment variables are validated at read time.** Required: `PORT`, `DB_HOST`,
  `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_SSLMODE`, `JWT_SECRET`,
  `CORS_ORIGINS`. A required variable that is unset must terminate startup with a
  message naming it. Only `PORT` (default `8080`) and `CORS_ORIGINS` (default: the Vite
  dev origins) may fall back. The `WS_*` tuning variables read in
  `hub.ConfigFromEnv` are also optional, and each is validated: a value that does
  not parse, or is zero or negative, is a startup error rather than a silent
  fallback.
- **No dead code, no commented-out code, no `TODO`/`FIXME` in merged code.** Delete
  it. If work is unfinished, do not merge the branch.

### 2.2 Future-Proofing

- **Every change must be additive by default.** New behavior extends existing behavior.
  Rewriting working code to a new shape is prohibited unless the rewrite is the task.
- **Public interfaces are contracts.** HTTP route paths and methods, JSON field
  names, `db.Querier` method signatures, SQL column names, exported Go and
  TypeScript symbols, cookie names, and message payload shapes. Changing one
  requires backward compatibility or an explicit new version plus a migration
  path for existing clients. Silent renames are prohibited. JSON fields are
  `snake_case`, new fields are optional, removal requires a deprecation cycle,
  and clients must tolerate absent fields.
- Partial updates use `PATCH` with pointer fields so "absent" is distinguishable
  from "zero". Never infer intent from a zero value.
- **Migrations are forward-only.** Append `backend/sql/schema/NNN_name.sql`. Never edit
  an already-applied migration, and never drop or rename a table or column. Destructive
  changes require a written migration plan in the pull request.
- **No hard-coded shortcuts that must be torn out later.** When a value is
  policy- or environment-dependent (limits, timeouts, hosts, ports, durations,
  origins), it lives in exactly one named constant in the module that owns the
  policy; new inline magic literals are prohibited. The base URL in `api.ts` and
  the pagination limits in `messages.go` are known instances — consolidate them
  when you touch them, never scatter more.
- **No speculative generality.** No feature-flag systems, plugin registries, strategy
  maps, configuration layers, or "for future use" parameters without a current use.

### 2.3 Scalability & Modularity

- **Separate concerns into modules with minimal interfaces.** A module exposes
  the smallest surface that fully serves its callers.
- **Every module must be independently testable.** If a unit cannot be tested
  without booting the whole server or a live browser, its dependencies are
  wrong — inject them. Composition over inheritance is the default.
- **No hidden global state.** Dependencies are passed as parameters. New
  package-level mutable variables are prohibited. Read-only constants are the
  only permitted package state; `constants.USER_COLORS` must never be mutated at
  runtime.
- **Code must scale in three directions.** A design that only works at small
  scale is rejected in review.
  - More data: every query returning a variable number of rows is bounded by a
    server-side `LIMIT`. Client-side truncation does not count.
  - More users: no shared mutable state across requests, no unbounded in-memory
    growth without eviction. The per-IP rate limiter in `routes.go` is currently
    unbounded and multi-instance-incorrect; document that limitation and replace
    it with a shared store before scaling horizontally. The WebSocket hub in
    `internal/hub` is **single-instance by design**: its room fanout is in-process
    memory, so a second backend replica would deliver events only to its own
    connections. It is bounded (`WS_MAX_CONNECTIONS`, `WS_MAX_ROOMS_PER_CONNECTION`,
    `WS_CLIENT_QUEUE_SIZE`, `WS_MAX_FRAME_BYTES`) and every bounded queue drops or
    closes rather than growing, but running more than one replica requires
    replacing the hub with a shared pub/sub backend first.
  - More contributors: one resource per file in `internal/routes`, routes
    registered only in `MakeRouter`, no cross-file edits outside a resource.
- **Authorization is server-side, per request, and resource-scoped.** Never trust
  a frontend route group, a hidden button, or a client-supplied user id as proof
  of access.
- **No N+1 access patterns.** One query per request path per resource, or a join.
  A loop issuing a query per iteration requires written justification in the diff.

### 2.4 Simplicity First

- Choose the simplest solution that fully solves the stated problem and satisfies
  §2.1–2.3. Simplicity never overrides correctness. **Every line must justify
  its existence:** if you cannot name what breaks when it is deleted, delete it.
- **Standard library and existing project utilities first.** Prefer
  `net/http`, `encoding/json`, `crypto/rand`, `context`, `errors`, `slices`,
  `time` over any new module. On the frontend, prefer what `api.ts`, `utils.ts`,
  `@hermitk/bluenite`, and `lucide-svelte` already provide.
- **Adding a dependency requires written justification** in the pull request:
  what it replaces, why the standard library or an existing dependency is
  insufficient, and its maintenance status. A new dependency with no
  justification is rejected, not debated.
- No wrappers that only forward, no single-use abstractions, and no configuration
  for a value with exactly one setting. Functions stay readable in one screen;
  longer ones are split into named steps.

### 2.5 Agent Behavior

- **Read this file before making any change.** No exceptions.
- **Do not invent requirements.** If the task is ambiguous, stop and ask. A
  wrong guess implemented confidently is worse than a question.
- **Run the project's tests and linters before declaring a task complete**
  (§6). A task with a red check is not done. Never claim a command ran when it
  did not, and report failures with their output.
- **Do not modify files outside the scope of the task.** Unrelated
  refactoring, reformatting, and drive-by renames are prohibited in the same
  change. If an unrelated problem is found, report it, do not fix it.
- **Prefer editing existing code over creating new files.** A new file requires
  a stated reason for why the existing file cannot hold the change.
- **Leave the codebase so the next agent can continue without context loss.**
  Update this file when a rule becomes wrong or a convention changes.

## 3. Code Standards

### 3.1 Backend — Go

- Handlers follow the existing shape exactly: a factory returning `http.HandlerFunc`,
  taking dependencies as parameters, e.g. `func sendMessage(q db.Querier) http.HandlerFunc`.
- **New request/response DTOs must be unexported** (`registerRequest`,
  `updateUserSettingsRequest` pattern) unless another package consumes them.
  Existing exported DTOs are grandfathered; do not propagate the inconsistency.
  DTO JSON tags are `snake_case` and are wire contracts (§2.2).
- Package-private helpers in `internal/routes` keep the leading-underscore convention
  already used by `_isValidParticipant`, `_isRoomCreator`, `_isMessageSender`, and
  `_validateReplyTo`. A helper that writes its own error response and returns `bool` must
  document that in a doc comment.
- **Always use `r.Context()`** for queries. Never `context.Background()` inside
  a handler.
- Wrap errors with context using `%w`; use `errors.Is` / `errors.As` to branch.
  Compare `pgx.ErrNoRows` and `*pgconn.PgError` codes, never string matching.
- **Realtime transport.** `internal/hub` is a dumb in-process fanout with no
  knowledge of rooms, users, or messages; authorization and payload shape belong
  to `internal/routes/websocket.go` and `messages.go`. The socket is push-only —
  every write still goes through the REST endpoints, and a push that fails is
  logged but never changes the HTTP response. Frames are
  `{"type": ..., "data": {...}}` in snake_case, and the event names live in
  `constants` next to their `frontend/src/lib/types.ts` counterparts. A
  subscription is authorized against the database on every subscribe frame, and
  a non-participant is closed with `StatusPolicyViolation`.
- `pgtype` wrappers are the null model. A nullable column is never faked with a
  sentinel value.

### 3.2 Database & sqlc

- **Never hand-edit `backend/internal/db/`.** Those files carry
  `Code generated by sqlc. DO NOT EDIT.` Change `sql/queries/*.sql` or
  `sql/schema/*.sql` and run `sqlc generate`.
- Every SQL statement lives in `sql/queries/` with a `-- name: X :one|:many|:exec`
  directive. No inline SQL in Go, ever.
- Every new column is nullable or has a default; backward compatibility with
  existing rows is mandatory.
- Authorization predicates belong in the query (`WHERE sender_id = $2`), not
  only in the handler, so the database is the final enforcement point.
- Adding a method to `db.Querier` is additive and allowed. Removing or retyping
  one requires updating every call site in the same change.

### 3.3 Frontend — SvelteKit / TypeScript

- Prettier and ESLint are the source of truth: single quotes, no semicolons, 100-column
  width, 2-space indent, trailing commas, LF, `arrowParens: always`. Run
  `npm run format` rather than hand-formatting.
- **All backend access goes through `src/lib/api.ts`.** Calling `fetch`
  anywhere else is prohibited. New methods reuse the private
  `this.request<T>()` helper so credentials, error extraction, and 204 handling
  stay uniform.
- `Api` methods return `ApiResponse<T>` (`{ data, error }`) and never throw. Callers must
  branch on `error`; ignoring it is prohibited. Prepend `getValidAuthToken()` to every
  authenticated method and never read the raw cookie for authorization decisions.
- `api.ts` uses a single in-flight refresh promise so concurrent requests share
  one renewal. Any new token-refresh path must preserve that property.
- **All WebSocket access goes through `src/lib/realtime.ts`.** Constructing a
  `WebSocket` anywhere else is prohibited, and `api.ts` stays the only source of
  `API_BASE_URL` — the socket URL is derived from it by `websocketUrl()`. The
  socket factory and token source are injected into `RealtimeClient` so reconnect
  and dispatch logic is testable in plain Node with a stub socket; keep it that
  way rather than reaching for a global. The client owns the connection, the
  backoff, and the watched-room set; pages only register handlers and call
  `subscribe`/`unsubscribe`, and a page must unsubscribe the room it is leaving
  so the backend stops fanning a room nobody is reading. The socket is
  push-only: a received event merges through `upsertMessage`, and a lost event
  is repaired by the REST refetch, never by a replay protocol.
- No `any`. No non-null assertion `!`. No `@ts-ignore` without a linked reason
  in a comment.
- Svelte components use runes only (`$state`, `$derived`, `$props`); runes mode
  is forced project-wide.
- Shared types live in `src/lib/types.ts`; pure helpers in `src/lib/utils.ts`;
  route-local logic stays inside the route. Nothing in `src/lib/server/**` may
  be imported by client-side code.
- A component renders explicit loading, error, and empty states; silent empty UI is
  prohibited. `console.log` is prohibited in committed code; `console.error` is for
  genuine error reporting, never a substitute for a user-visible state.
- Secrets never reach the client bundle. `access_token` is non-HttpOnly by design;
  `refresh_token` is HttpOnly server-side and must never be read by client code.

### 3.4 Error Handling & Logging

- Status codes are fixed by failure class: `400` invalid input · `401` bad auth ·
  `403` not permitted · `404` absent · `409` unique conflict · `429` rate limited ·
  `500` unexpected.
- **A `500` must also log the underlying error.** Handlers currently discard the wrapped
  `err` after `utils.WriteError`; when you edit one, add the log line with the chi
  request ID from `middleware.GetReqID(r.Context())`.
- Client-facing messages are generic and never include SQL, stack traces, file
  paths, tokens, or hashes. Detail goes to the log, formatted lowercase and
  action-first: `log.Printf("send message failed: %v (req=%s)", err, reqID)`.
  Never log passwords, password hashes, JWTs, refresh tokens, or cookie values.
- **A secret in a URL must be redacted before the logger sees it.** The `/ws`
  handshake carries the access token in the query string, and chi's
  `middleware.Logger` renders `r.RequestURI` into its log line *before* the
  handler runs. Redacting inside the handler is too late. `redactWebSocketToken`
  in `routes.go` clears `r.RequestURI` and is registered ahead of
  `middleware.Logger`; any new route that accepts a credential in the query
  string needs the same treatment there, and `r.URL` is what the handler reads.
- Responses are written only through `utils.WriteJSON` / `utils.WriteError`.
  Writing headers or encoding JSON directly in a handler is prohibited.

### 3.5 Testing

- The realtime path is the first covered code in the repository. Every change
  adds tests; this is not optional and not deferred to a follow-up.
- **Backend:** `go test ./...`. New handlers are tested with `httptest` against
  a fake `db.Querier`; prefer declaring the handler parameter as `db.Querier` so
  a fake can be injected (`*db.Queries` only where `WithTx` is used). Cover every
  new validation branch, every new error path, and every authorization denial.
- **Frontend:** `npm test` (Vitest, `server` and `client` browser projects).
  `requireAssertions` is enabled — every test must assert.
- **Bug fixes require a regression test that fails before the fix and passes after.**
  If you cannot write one, the fix is not understood. Test names state the
  behavior: `TestSendMessageRejectsEmptyContent`.

## 4. Architecture Rules

### 4.1 Dependency Direction (strict, no cycles)

```
cmd/server → routes → { auth, db, hub, utils, constants }
                 auth → { db, utils, constants }
                 hub   → (transport only: no routes, auth, db, or domain types)
                        db → (generated data only)
                     utils → constants
                  constants → ∅
```

- `constants` and `utils` must not import `routes`, `auth`, or `db`; `auth` must
  not import `routes`; `internal/db` imports nothing from `internal` — it is a
  leaf. Any import that would create a cycle is a design error. Restructure; do
  not work around it.
- `hub` is a leaf below `routes` for the same reason: it moves bytes to sockets
  and knows nothing about rooms, participants, or messages. If you find yourself
  wanting a query inside `internal/hub`, the call belongs in `internal/routes`.

### 4.2 Module Boundaries

- One resource per file in `internal/routes`: `rooms.go`, `messages.go`,
  `user.go`, `settings.go`, `refresh_token.go`. A new resource gets a new file.
- Routes are registered **only** in `MakeRouter` (`routes.go`), with rate limits
  and auth middleware declared there. Registering a route from anywhere else is
  prohibited.
- Authentication state is passed through `context` under
  `constants.UserIDContextKey` and read with `utils.GetUserIDFromContext`.
  Handlers must not read tokens directly. `/ws` is the one deliberate exception:
  a browser cannot set an `Authorization` header on a WebSocket handshake, so
  `serveWebSocket` validates its own token from `constants.WSAuthQueryParam`
  through the exported `auth.ValidateJWT`.
- `utils` holds only pure, stateless helpers. If a helper needs state, it does
  not belong there.

### 4.3 Interface Stability

- The public surface — HTTP routes, JSON shapes, cookie names, `db.Querier`, the
  `utils` write/validate helpers, `auth.JWTAuth`, the `Api` methods in `api.ts`, and
  every type in `types.ts` — is a contract. Changing it requires a written migration
  note, backward compatibility, or an explicit version bump. Adding to it is always
  allowed and is the default way to extend behavior.
- The realtime wire contract is part of that surface: the `message_created`,
  `message_updated`, and `message_deleted` event names, the
  `{"type", "data"}` frame envelope, the `subscribe`/`unsubscribe` client frames,
  and the `constants.WebSocketPath` / `WEBSOCKET_PATH` route are pinned on both
  sides. A deployed client and a running server may be different versions, so
  add a new event rather than renaming an existing one, and make the client
  ignore an event type it does not recognize.

### 4.4 Configuration & Local Development

- Backend configuration is read from the environment at process start, in one place
  per concern, and validated immediately (§2.1). No config file, no `os.Getenv`
  calls in handlers.
- Secrets (`JWT_SECRET`, `DB_PASSWORD`) come from the environment only. The
  value currently in `docker-compose.yml` is a local development default and
  must never be reused as a production value.
- The frontend API base URL is defined once in `src/lib/api.ts`. Do not
  hard-code `http://localhost:8080` anywhere else.
- The WebSocket tunables are read once, in `hub.ConfigFromEnv`, and each has a
  default in `hub.defaultConfig`, so `docker-compose.yml` does not need to set
  them: `WS_MAX_CONNECTIONS` (1000), `WS_MAX_ROOMS_PER_CONNECTION` (50),
  `WS_CLIENT_QUEUE_SIZE` (64), `WS_MAX_FRAME_BYTES` (4096), `WS_PING_INTERVAL`
  (30s), `WS_WRITE_TIMEOUT` (10s), `WS_SHUTDOWN_TIMEOUT` (5s). Add a new one to
  `Config`, `defaultConfig`, and `ConfigFromEnv` together, never to a call site.
- `docker compose up` must bring up a working system on a clean checkout: Postgres
  on `5433`, backend on `8080`, schema applied from `backend/sql/schema`, and
  `GET /health` returning `{"status":"OK"}`.
- After a `.sql` change, `sqlc generate` must be run and the regenerated
  output committed, so `go build` succeeds without the sqlc toolchain.

### 4.5 Working Tree, Commits & Host Environment

- Branch from `main` for feature work. Commits use the conventional prefixes already in
  history (`feat:`, `fix:`), one logical change per commit. Run `git status` before and
  after a task to confirm only intended files changed.
- **The working tree contains uncommitted user work.** Treat it as read-only
  unless the task names it. Never discard, overwrite, or stash changes you did
  not make.
- **Never modify files outside this repository**, including `node_modules/` and
  the external `@hermitk/bluenite` package. Do not touch `package-lock.json`
  except through `npm ci`/`npm install` when a dependency actually changes.
- Never commit secrets, `.env` files, or build artifacts; the credentials in
  `docker-compose.yml` are dev-only.
- Ports: Postgres `5433` (container `5432`), API `8080`, Vite `5173` (CORS also
  allows `5174`).
- After exercising the stack, run `docker compose down`. `down -v` deletes the
  Postgres volume and is destructive — it requires explicit confirmation. Never
  remove the compose healthcheck, schema-init mount, or network wiring without
  exercising the full stack first.

## 5. Definition of Done

A task is complete only when every box below is checked. If one cannot be
checked, say so explicitly instead of claiming completion.

**Scope and honesty**
- [ ] Changes are limited to files the task required, every applicable rule is
      satisfied, and no dead code, commented-out blocks, or `TODO`/`FIXME` remain.
- [ ] Nothing is described in the summary that was not actually run or verified.

**Backend**
- [ ] `sqlc generate` produced no diff beyond the intended one.
- [ ] `gofmt -l .` prints nothing; `go vet ./...`, `go build ./...`, and
      `go test ./...` all pass, including new tests.
- [ ] Every new input is validated; every new error path returns a correct status
      code and logs the underlying error with a request ID.
- [ ] Every new endpoint is registered in `MakeRouter` with the correct rate
      limit and auth placement, and authorization is enforced server-side and,
      where applicable, in SQL.

**Frontend**
- [ ] `npm run check` (svelte-check), `npm run lint` (prettier + eslint), and
      `npm test` all pass, including new tests.
- [ ] All network access goes through `api.ts` and handles `error`.
- [ ] All WebSocket access goes through `realtime.ts`; a page that leaves a room
      unsubscribes it, and a dropped connection shows a visible state.
- [ ] Loading, error, and empty states render for anything asynchronous.

**Contract**
- [ ] No public interface changed without a written migration note, and any API,
      DTO, or config change is reflected in `types.ts` and `api.ts`.
- [ ] Anything a future agent would need to know is written down — in code comments
      where it belongs to code, or by updating this file. If the change crosses the
      frontend/backend boundary, the full stack was run and verified in a browser.

## 7. Prohibited Practices

Each of the following is a review rejection.

**Robustness**
1. Swallow an error, continue past a failed invariant, or return a zero value as
   a stand-in for a failure.
2. Add `panic`, an empty `catch`, or a silent `if err != nil {}` in a request path.
3. Read a body, path param, query param, or cookie without validating it.
4. Default a required environment variable to a silent fallback.
5. Merge commented-out code, `TODO`, `FIXME`, or "temporary" logic.
6. Write a `500` without logging the underlying error.
7. Let a credential reach the access log — including a query-parameter token
   that `middleware.Logger` renders before the handler runs (§3.4).

**Future-proofing**
8. Rename, remove, or retype a route, JSON field, cookie name, SQL column, or
   exported symbol without a migration note.
9. Edit an already-applied migration, or drop/rename a live table or column.
10. Infer "not provided" from a zero value in an update payload.
11. Add a magic literal where a named constant belongs, or a second source of
    truth for a value that already has one.
12. Build config layers, registries, or abstractions for requirements that do
    not exist.

**Scalability & modularity**
13. Introduce a package-level mutable variable, singleton, or init-time global.
14. Register routes outside `MakeRouter`, add a reverse import, or create a cycle.
15. Hand-edit anything under `backend/internal/db/`.
16. Write inline SQL in Go instead of `sql/queries/`.
17. Return an unbounded collection, or issue a query per row in a loop.
18. Trust the client for authorization, or enforce ownership only in the frontend.
19. Call the backend from outside `src/lib/api.ts`, or open a `WebSocket`
    outside `src/lib/realtime.ts`.
20. Put a query or a domain decision inside `internal/hub`, or let the socket
    become a write path.

**Simplicity**
21. Add a dependency without written justification in the pull request.
22. Add a wrapper, interface, or option with one caller and one implementation.
23. Keep code you cannot justify line by line. Delete it.

**Agent behavior**
24. Invent requirements, guess at ambiguity, or assume a contract change.
25. Modify files outside the task's scope, or bundle unrelated refactors.
26. Create a new file when editing the existing one would do.
27. Declare a task complete without running §6, or report a command as passing
    when it was not run.
28. Leave a non-obvious decision in your own reasoning instead of a code comment,
    a test name, or this file.
